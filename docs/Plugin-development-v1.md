日期：2026-11-03  
适用主体：Hhub 0.5，后续版本沿用并按接口版本演进。  
状态：本轮讨论确认的开发基线。本文定义验收要求，不表示现有插件和主体已经全部实现。

2026-11-04 产品范围补充：默认设备列表面向键盘、鼠标、耳机、手柄等游戏外设。内置指针/触控板、摄像头和系统内部控制器不因能被 Windows 枚举就进入该列表。插件声明产品信息及能力时须遵循此范围；主体底层诊断信息不等于默认用户设备列表。

## 1. 插件与主体的关系

插件可以独立开发、交付、安装、升级和卸载；在 Hhub 中使用时，界面与生命周期由 Hhub 承载和管理。

主体只提供通用能力和稳定接口。接入新品牌、新设备或新功能，不得要求主体新增对应插件的专用代码。需要新增公共能力时，应扩展通用接口，并声明兼容版本。

第一版不允许插件之间形成强依赖。插件只依赖主体公开的公共接口，不读取其他插件的私有文件、不直接调用其内部实现。可选的跨插件协作留待后续规范。

主体提供设备基础识别、插件管理、场景协调及公共界面规范；具体设备协议、数据采集与处理、设备名称和图片、电量、可调参数由插件提供。系统监测的数据采集和处理也属于插件职责。

## 2. 运行环境与进程

- 官方插件默认使用 C# / .NET 10。
- 后台业务在独立进程中运行，由主体负责启动、通信和停止，不自行弹出控制窗口。
- 默认复用主体软件包提供的运行环境，不要求用户另行安装一套 .NET，也不在每个插件包中重复携带同一运行时。
- 特殊情况下允许插件自带运行环境，但必须声明用途、版本、架构、额外体积和清理方式。
- WebUI 是界面形式，不代表插件必须另带 Node.js。只有后台确有需要时，才按特殊运行环境处理。

共享运行环境与独立后台进程必须同时成立。主体应提供受支持的后台启动方式；仅发布一个自包含的主体 EXE，并不能证明任意插件 DLL 都能使用其运行环境启动。

独立调试和测试工具可以存在，但不能成为普通用户从 Hhub 使用插件时必经的另一个软件。

## 3. 界面承载

顶栏和侧边栏始终归主体管理，其余内容区供插件展示自身界面。插件可以拥有 Hhub 内的内容页面；禁止把核心控制界面转移到另一个窗口或另一个应用中。

支持原生 WinUI 与 WebUI。插件自行组织内容区布局、图像和交互，主体不能强制把任意复杂界面变成“执行按钮＋状态方块”的通用面板。

插件须遵循主体提供的深浅色主题、字号层级、间距、图标尺度、焦点和交互规范，支持窗口尺寸及 DPI 变化。主题切换应即时生效，无需重启，不得导致崩溃。

界面应简洁、对齐、减少无效留白。能直接表达的状态不新增按钮，不堆叠小字说明；详细原因按需展开。无配置、无传感器、缺少依赖等状态应如实展示，不能提供没有实际能力的控件。

可通过错误外框、禁用态等表现状态，同时保留可访问的原因说明，不能只靠颜色传递信息。优先在已有页面内选择和编辑，避免无必要的独立页面、弹窗和滚动。

功能型插件可以声明侧栏入口，由主体统一排列和打开。设备名称、图片等展示信息也通过通用声明或数据接口提供，不写入主体品牌分支。

侧栏图标可使用 `navigation.glyph` 系统字体符号，或 `navigation.pathData` 的直线矢量路径（M/L/H/V/Z，最多 2048 字符）。使用矢量路径时声明 `navigation.path.v1` 能力。图标由主体统一尺寸并继承界面前景色，适应深浅主题；主体不按插件 ID 特判品牌图标。

## 4. 按需启动与后台保活

所有插件必须支持按需启动。打开页面、相关设备需求、执行命令、场景动作和持续任务可以形成运行需求；单纯安装完成不能成为永久驻留理由。

离开页面后仍有持续任务时，可以继续运行，但插件必须声明任务及保活原因，例如正在处理音频、采集用户需要的电量、执行场景所需的持续监测。不得只上报一个无法解释的“保持运行”。

持续任务结束，且没有页面、命令或其他需求时，后台进程自动退出。关闭页面与结束持续任务是不同操作。

关闭主窗口进入托盘，已有持续任务继续。用户明确选择“退出 Hhub”时，主体要求插件保存必要状态、释放资源并停止，不留下自行驻留的孤立进程。

用户可以主动停止或禁用插件，插件不能凭保活需求抵消这一选择。停止前只有确实会中断任务或影响恢复时才提示，不反复确认。正常清理失败或超时必须报告，不能把强制结束当作已经成功恢复状态。

## 5. 权限和外部依赖

### 关于页披露（2026-11-05）

新开发及更新的插件必须在 `plugin.json` 中提供 `disclosure`，让主体在“设置 → 关于”中展示插件自身许可、采用的开源项目、署名、运行环境与依赖。不得只列一个项目名称，省略使用的版本、许可证或原作者署名。许可原文必须随插件包交付，字段路径相对于插件根目录。详细字段示例见 [插件披露格式](Plugin-disclosure-v1.md)。

声明存在时，主体在预检、安装与加载阶段校验格式与许可文件；缺少许可文件的新版包不得替换已安装版本。旧 API-1 插件为兼容仍可加载，但关于页明确标注“尚未提供结构化声明”，并呈现包内已有的依赖清单与许可原文；旧插件的兼容处理不代表其已满足新版交付要求。

安装前展示插件声明的权限和额外依赖。权限应对应实际需求，例如设备通信、系统设置修改或联网，不能无理由要求全部权限。

主体接口必须检查权限，不能允许未声明、未获准的调用。插件不能通过界面桥接绕过检查，也不能把网页消息直接映射为任意本地命令。

权限声明、接口检查和操作系统级隔离是不同层次。独立进程不是沙箱；原生插件绕过主体直接调用系统 API 的限制，需要额外的隔离或受控代理机制。实现之前，不得对外宣称插件已经受到完整权限隔离。

缺少驱动、运行环境或权限时，仍允许打开内嵌页面，明确说明哪些功能受影响。在插件页面或相关系统详情中提供安装、帮助或授权入口，不在主页堆放依赖按钮。

额外驱动安装和权限提升由用户主动触发，不静默安装或提升整个主体权限。依赖处理失败时保留明确状态，不伪装成功。

## 6. 设备身份与真实状态

VID/PID 用于匹配产品支持范围，不能独自区分同型号设备。每次操作还必须核对真实设备实例、关联接口和连接状态。

主体可以归并同一物理连接实体的多个接口，但必须向插件保留所需的关联信息。两个相同型号设备不能因 VID/PID 相同而合并。一个接收器配对多个设备时，具体配对对象由具备相应能力的插件提供。

设备能枚举出来，不等于通信已确认；通信已确认，也不等于所有功能都支持。插件必须区分未连接、不支持、依赖缺失、通信失败、状态过期、执行中和已确认成功。

设置写入应通过设备回读或其他可验证结果确认。仅调用成功或发送完成不能当成设备已经生效；无法确认时明确标记未确认。缺少温度、电量等读数时返回不可用，不能编造数值或把旧数据当实时状态。

设备默认没有配置。主体只展示插件实际声明的配置、命令和场景能力，不生成假的默认配置。

## 7. 场景与资源冲突

插件应声明可用于场景的动作、参数、作用设备以及被修改的资源。页面操作和场景动作使用同一套能力与结果反馈，不能各自维护互不一致的配置。

主体统一协调同一资源的控制权。例如两个插件修改同一鼠标的 DPI 时，必须识别为冲突，交由用户选择，不能在后台互相覆盖。不同设备的同名设置不是同一个资源。

资源声明必须足以识别实际目标，不能只使用各插件内部自定义且互不对应的名字。控制权交接前须完成必要的停止、释放或状态处理；未完成时不能宣称交接成功。

冲突未解决前不得执行互相覆盖的写入。自动场景不能绕过用户已经作出的控制权选择；提示和错误应集中呈现，避免持续重复弹出。

## 8. 配置保存与状态恢复

插件须声明哪些内容是用户保存的持久配置，哪些是运行期间的临时系统修改，以及停止、退出、升级、卸载时分别如何处理。

不能统一规定所有修改都恢复：设备板载配置可以需要保留，临时音频路由等可以需要恢复。用户必须能够理解具体行为。

需要恢复的修改应保存必要原值，并验证目标身份。用户后来主动修改的状态不能被旧备份无条件覆盖。恢复失败必须明确报告，不以进程退出代替恢复成功。

## 9. 插件包、升级和兼容性

插件包至少提供以下信息；这是信息要求，具体字段沿 SDK 定义，不在本文另造一套清单格式：

| 信息 | 要求 |
| --- | --- |
| 身份 | 稳定插件 ID、名称、作者、版本 |
| 兼容性 | 最低主体版本、接口版本、所需公共能力 |
| 运行 | 后台入口、目标架构、共享或特殊运行环境需求 |
| 界面 | 内嵌入口、WinUI / WebUI 资源、可选侧栏入口 |
| 能力 | 设备支持范围、命令、参数、资源及场景能力 |
| 生命周期 | 按需启动条件、持续任务、停止和清理行为 |
| 权限与依赖 | 所需权限、驱动和其他外部依赖 |
| 数据 | 配置、缓存、日志的位置及卸载保留策略 |

兼容性在启用前检查。不满足主体版本、接口或能力要求时阻止启用，在插件管理中说明原因，不能先加载代码再碰运气。

插件市场、本地选择、拖入和随附包共用宿主的安装逻辑。用户主动安装或更新时，确认页展示来源、目标版本、声明权限和已声明的运行环境及依赖。随附的监测插件首次可由宿主安装，后续自动更新仅接受没有新增权限或依赖声明的版本。用户主动卸载后，宿主记住该选择。

常规更新必须提高版本号。同版本重装可通过先卸载再安装完成。升级和卸载前，插件应响应停止请求，保存必要状态、停止任务并释放资源。宿主暂存并校验新包，保留旧版直到替换提交。更新前正在运行的插件还会进行启动验证，有状态上报的插件需要在验证期间返回状态。替换或验证失败时恢复旧版，换包中断后下次启动尝试恢复。插件自身仍须保证配置迁移可恢复，宿主的版本回退只处理受管程序文件。

插件应将用户配置与程序文件分开存放，并在交付说明列出配置、缓存、日志和外部依赖的位置及所有者。单插件卸载清理受管程序、已知的版本备份和界面缓存，保留插件设置和场景引用。卸载 Hhub 时一并清理受管插件及运行缓存，默认保留可能含本地存储的 WebUI 浏览器数据。交互卸载可选择删除用户配置、场景和已知旧版插件数据。共享驱动和用户确认保存的系统更改继续由各自的管理入口处理。

市场审核、签名、仓库组织和自动更新策略未在本轮冻结，不把它们当成已经确认的第一版发布承诺。

## 10. 第一版验收

验收应覆盖真实功能与关键生命周期，不只检查页面能否打开：

1. 全新安装主体后，普通插件使用主体随附环境启动，无需用户另装重复运行时。
2. 从 Hhub 使用插件的全部核心控制均在内容区完成；不要求再开独立控制软件。
3. 新插件仅通过公共接口接入，主体不增加该插件专用分支。
4. 打开、离开、持续任务保活、任务结束、主动停止、托盘运行和完整退出符合规则。
5. 缺少依赖、设备断开、数据过期和执行失败能够正确表达，不宣称成功。
6. 同型号多设备能正确区分；资源冲突不会导致插件互相覆盖。
7. 覆盖同版本或低版本拒绝、运行中升级失败及中断恢复、单插件卸载后重装。确认保留的配置仍能读取，已卸载的随附插件不会自动恢复。
8. 覆盖宿主覆盖升级和宿主卸载后重装。覆盖升级保留插件与配置，默认卸载移除受管插件并保留配置，选择删除数据时清理宿主数据和已知的旧版插件数据。
9. 深浅色、DPI、窗口尺寸和界面重新进入时，主题及状态保持一致，资源正确释放。

性能应以空闲、打开页面和持续任务三种状态分别记录，不编造统一的内存或 CPU 承诺。测试优先覆盖实际风险；不为低影响样式修改堆叠只重复实现的测试。

## 11. 现有实现的使用方式

现有清单字段可参考 `src/Hhub.Core/Models.cs`；原生界面入口可参考 `src/Hhub.PluginUi`；现有 WebUI 用法见 [插件 WebUI 与设备展示](Plugin-WebUI.md)。这些实现资料不代替本准则的完整验收。

后续各插件对话应先按本准则检查差异，再修改对应插件。共享运行环境启动方式、带原因的后台保活、资源控制权和权限隔离等主体公共能力，需要单独核对实现状态，不能仅因文档已经确认就标记完成。

## 12. 已实现的 .NET 10 共享启动接口（2026-11-04）

公共能力名为 `runtime.dotnet10.shared.v1`。使用主体环境的 .NET 10 后台在清单中将 `entryPoint` 指向有 Main 入口的 DLL，使用 `transport: "stdio-v1"`，并在 `requiredCapabilities` 声明上述能力。界面仍使用现有 `uiAssembly` / UI API 1，不另起控制窗口。旧主体不认识该能力时在安装前拒绝，不尝试直接执行 DLL。

主体在自身目录提供 `Hhub.PluginHost.exe`、同名 DLL、deps.json 与 runtimeconfig.json。该通用入口复用主体软件包旁的运行库，每个后台仍是独立进程，参数、UTF-8 管道、回执、超时、停止及退出管理均沿用 stdio-v1。插件依赖通过自身 deps.json 解析；主体公共程序集和框架不复制进普通插件包。当前只支持 .NET 10、Windows x64；框架版本不匹配、入口缺失或启动失败会报告错误。此方式不提供操作系统沙箱。

主体发布会自动构建该通用入口，只复制 4 个入口文件到主体运行目录，共用已有运行库。仅有以前的自包含 Hhub.App.exe 仍不足以支持此能力，必须更新完整主体目录。原有 EXE 插件的启动路径继续兼容。

插件后台的推荐发布参数：`--self-contained false -p:UseAppHost=false`。包内保留插件业务 DLL、依赖元数据、UI DLL/页面资源、专用依赖及必要说明/许可证；不打包 SDK、系统运行库、主体公共契约或调试工具。Windows 游戏设置 0.3.1 已按该方式交付，其他历史插件不因此被自动视为已迁移。

共享运行环境的现有公共入口与打包约定见 [共享 .NET 10 插件后台入口](Plugin-shared-runtime.md)，能力名为 `runtime.dotnet10.shared.v1`。该入口不代表权限隔离或资源控制权已完整实现。

2026-11-04 监测授权补充：用户已明确同意，启用系统监测后自动申请仅限采集后台的 UAC。授权可以由 Windows 提示批准或取消；取消后停止自动重试并保存选择，主体及其他插件不得随之提权。这是监测采集的授权约定，不扩展为其他插件默认可自动提权。


## 当前 Desktop 的首页与托盘接入

插件沿用签名包的 `hhub.plugin/1` 标准输入输出协议 (`stdio-v1`)。主体通过 `hello`、`discover` 和 `read(targetId)` 读取状态。没有 TCP 端口。设备在切换 USB、2.4 GHz 等链路时应继续使用同一个逻辑目标 ID。两台同型号设备分别使用自己的 ID。

| 显示位置 | 清单 `provides` 中的能力 | `read` 返回的值 |
| --- | --- | --- |
| 首页详情 | `device.overview` 1.x 中的 `device.overview.parameters` | `[{"label":"回报率","value":"1000 Hz","compact":true}]` |
| 托盘电量 | `device.overview` 1.2 中的 `device.overview.battery-percent`，另声明权限 `device.battery.read` | `[76]`，未知时 `[]` |
| 托盘充电 | 同一服务中的 `device.overview.battery-charging` | `[true]`，和本次百分比对应，未知时 `[]` |
| 其他托盘变量 | `device.overview` 1.3 中的 `device.overview.tray-variables` | `[{"label":"连接","value":"2.4 GHz"}]`，每设备最多 4 项，标签最多 24 字符，值最多 48 字符 |

插件必须在清单 `capabilities` 定义每个字段的值结构。托盘读取仅使用在线、非模拟目标。插件在 `HHUB_PLUGIN_OVERVIEW_ONLY=1` 下只做短时、只读采集，未知或离线时返回空状态，不能用默认值填充遥测。电量通过独立电量字段提供，其他托盘变量使用单行文字。主体按设备逐行合并显示，超过 45 秒未更新的概览快照过期。旧 `tray.battery` 1.0/1.1 原生助手保留为电量兼容路径。

「首页显示详细参数」和「托盘显示电量」由主体按插件 ID 保存。鼠标插件的这两个开关位于「鼠标设置」标签页底部。关闭首页详情会停止读取该卡片的详细参数。电量与充电状态同时受全局和该插件的托盘开关控制。设备插件无需自行添加这两个开关。

## 旧版 Hhub.App 托盘电量接口与后台效率模式（2026-11-04）

主体提供通用能力 `device.battery.v1`，不在主体中实现厂商电量协议。插件可以在清单声明：

```json
"batteryTelemetry": { "refreshCommand": "refresh", "cacheSeconds": 120 },
"requiredCapabilities": ["device.battery.v1"]
```

`refreshCommand` 必须是该插件已经声明的 stdio 命令。主体在用户悬停托盘时，按需启动匹配已连接设备的插件并请求刷新；同一插件正在刷新时不重复请求，短时间内重复悬停有节流。命令通过现有 requestId/result 确认。数据仍由插件通过完整快照的 `devices[]` 提供：

```json
{ "devices": [ { "instanceId": "对应主体设备实例或其成员接口实例", "name": "设备名称", "battery": 76 } ] }
```

电量为 0–100 的实际百分比，缺失时使用 null。必须按实例对应，不能用 VID/PID 或型号给两台同款设备分配同一个读数。主体缓存的有效期由 `cacheSeconds` 指定（10–3600 秒，默认 120），后台停止后可保留到期前的读数；禁用插件、断开设备、明确上报不可用或缓存过期后不再显示旧电量。插件不能把已经过期的电量不断作为新读数发布。快照仍需遵守此前的真实状态要求。

托盘展开提示使用系统原生的独立文本区域，避免常规托盘 Tip 的 127 字符上限。插件不创建托盘图标或提示窗口；主体统一排版。未知电量显示“—”，不伪造 0%。鼠标插件 0.3.3 已通过此声明接入，其设备协议未写入主体。

主体隐藏时启用 EcoQoS、降低普通进程调度及内存页优先级；混合架构的软 CPU Sets 优先选择较低 EfficiencyClass 的核心，不做不可回退的硬绑核。恢复窗口时还原。共享托管启动器监听同一用户的手动重置事件 `Local\Hhub.BackgroundEfficiency.<用户 SID>`，后台进程自行改变自身调度，因此不需要主界面获得管理员后台的控制权限。事件置位表示后台效率模式，复位表示恢复；特殊运行环境也可以按此公共约定接入。

对延迟敏感的插件可声明 `latencySensitive: true`；主体不对其后台强制降速。已有声明 `audio.render` 的插件同样保留正常调度，以免影响持续音频处理。界面隐藏会释放页面、插件 UI 和图像引用，并正常停止无需求插件；不反复调用工作集清空来制造表面内存下降。后台效率模式不会豁免插件原有的生命周期要求。
