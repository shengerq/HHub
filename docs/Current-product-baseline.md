# HHub 现有产品与依赖核对

核对日期：2026-11-09。依据：本地源码、插件清单、相应说明及用户已确认的产品方向。本文件记录本轮理解与发现，不表示完成实机验收，不自行改变功能范围。

## 1. 已确认的产品目标

HHub 面向玩家和外设开发者，通过插件统一调节不同品牌的外设，减少多个臃肿厂商软件带来的负担。后台与前台资源占用、启动速度、按需运行和按需移除都是目标。

HHub 是选定的产品主体，保留已有页面与功能关系。GameHub 是插件、协议、开发流程和取证资料的来源。确立统一插件体系后重写插件，不建立强兼容所有历史插件的适配层。

轻量不意味着删除已有页面依赖的功能。系统监测为主页提供数据，属于现有产品功能；独立插件实现、是否随附、是否自动安装、何时运行、用户是否停用，是五件不同的事，不能混为“插件都不提供”。

第一台优先摆脱厂商驱动的设备是雷柏 VT3X Max；VT3 Pro Max 是另一只鼠标。目标是保留除固件升级外的官方功能，并覆盖有线和无线接收器。旧材料中的 VT3S MAX 不能直接当作这两款鼠标的身份或支持证据。固件升级延期，主题包仅为后期提案。

## 3. 随附、安装和运行的实际区别

当前 `tools/Build-Preview.ps1` 发布系统监测，并将监测、Windows 设置和音频包放入 `bundled-plugins`。这些包不应一概描述为“全部自动运行”。

`MainWindow.InitializeServicesAsync` 调用 `EnsureBundledMonitorAsync`，为主页准备系统监测：无监测时从随附监测包安装，但尊重用户移除记录；已有监测时只考虑同 ID 的较新随附包，且检查权限及披露依赖没有扩大。随后按运行需求调度。

未配置远程市场时，插件市场页可展示随附包。Windows 设置和音频随附包的存在不等于它们被上述监测初始化函数自动安装。

`PluginDemand` 综合可见页面、打开的插件、设备需求、执行中的命令、嵌入页面和后台活动。托盘隐藏会释放不可见页面需求；音频实际处理、远控服务等仍需根据任务状态保活。手机请求监测会形成有时限的监测需求，不能只以主页是否可见判断采集需求。

当前 `PluginMode` 经 `UnifiedMode` 归一后只保留按需/停用；旧文档中“按需/常驻/停用”三模式的说法不能直接视作当前界面行为。此处先记录差异，不自行恢复或删除模式。

## 5. GameHub 材料应如何使用

`gamehub/v3` 是当前 .NET 10 / WinUI 3 路线，分 App、Agent、Core、Contracts，含 C# / C++ SDK、开发包工具、结构化能力、事务和认证流程。其流程文档明确区分模拟自动检查、真实硬件与生产审核，不将已有测试数字当成本轮重新通过的结果。

`gamehub/相关素材/GameHUB` 是较早 C++ / Qt 工程及更细的设备研究资料，包含协议证据、设备支持矩阵、Rapoo / ROG 专项计划和实测记录。`GameHUB-V2-Qt` 另为归档分支；它们与 v3 不能作为同一份现行实现混用。

Rapoo 材料主要指向 VT3S MAX。资料明确区分设备身份、连接态、只读观察、协议验证和安全写入。某份材料记录的 PID 或 Motion Sync 读写，不证明所有连接或所有型号的全部能力已经可用；较早只读记录与较晚专项结论还需按日期、范围和源码关联核对。

- `gamehub/相关素材/GameHUB/05-docs/README.md`。

## 6. 新接口预览与现有产品的差距

现有 `MainWindow*.cs` 仍保留。新增 `UnifiedWindow` 仅在 `UseUnifiedHost=true` 条件构建中使用，并非已完成的正式界面整合；不能用这个预览的简化页面替换用户选择的现有产品。

| 现有需求 | 新预览当前差距 |
| --- | --- |
| 主页监测和设备概览 | 新预览缺少已有主页接入，发布脚本还断言不含任何随附插件；该断言不能作为当前产品验收标准 |
| 缺失温度/电量及过期数据 | 值合同目前不接受 null，完整读取要求能力值齐全，尚未覆盖现有不可用、缓存和过期语义 |
| 专业原生 / WebUI 页面 | 当前只提供通用能力编辑表单，没有替代已有 UI 模块及上下文的完整合同 |
| 耳机与 FXsound 协作 | 服务声明与匹配仅是子集，缺少已有页面嵌入、目标定位、命令路由及生命周期闭环 |
| 场景和配置拖放 | 当前预设 apply 不等于现有命名配置、应用识别、资源冲突和场景调度已迁移 |
| 手机、托盘和后台任务 | 布尔 backgroundActivity 不足以独立覆盖现有需求来源、释放、远控桥与用户停用行为 |
| 现有设置和插件私有数据 | 新预览只处理自己目录中的预设容器，尚未覆盖既有偏好、场景及分散的插件私有数据迁移 |
| 主体安装 / 更新 / 卸载 | 新预览新增的是隔离目录内的基础安装与清理；没有覆盖上述产品依赖、旧数据、跨版本更新和系统依赖的完整验收 |

之前预览的自动检查及 17 项安装器检查只证明被检查的局部流程。安装器测试已移除临时注册的 HHub 测试安装；测试日志保留在工作区归档中。它们不能证明产品功能完整，更不能抵消主页监测缺失。

## 7. 后续改造的依据

1. 以现有 HHub 页面和可用行为作为保留清单，先补齐统一接口对这些行为的表达能力。
2. 系统监测是必须覆盖的真实使用链路，不能继续只凭模拟鼠标和模拟 EQ 判断接口足够。
3. 同时覆盖设备插件、功能插件、页面供给、监测供给、配置/场景和跨插件协作；分类不能要求每个插件同时实现所有功能。
4. 保留与重写是两个层面：功能及用户数据要保留，内部代码按确定的新接口重写；不因此引入历史万能适配层。
5. 安装清单、默认提供策略和卸载所有权必须与真实功能依赖对应；不得先删除依赖，再把不完整页面当作轻量化结果。
6. 先把上述差距核对清楚，再恢复代码改造；本轮只建立事实清单，不新增功能或调整默认分发策略。
