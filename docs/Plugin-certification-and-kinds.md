# 插件认证与功能分类

日期：2026-11-09。状态：按用户最新约束收敛的设计，尚未实现为新 SDK。Hhub 主线、统一合同与重写旧插件的方向不变。首版采用集中审核认证，暂不建设通用沙箱、复杂硬件代理和多级证书授权平台。本文件替代此前安全草案中的强制隔离交付要求。

## 1 适合个人维护的认证方式

普通模式只运行 Hhub 项目认证的具体版本包。第三方可以开发并提交插件，但自行签名不等于项目认证。初期只维护一套项目认证密钥，私钥不进入仓库、不随 SDK 分发、不交给插件作者。

认证表示审核通过、来源可追溯及包内容未被修改，不表示绝对无病毒或无漏洞。界面使用“已认证”“未认证”“认证已撤销”，不显示“绝对安全”。认证是包准入机制，不是运行时沙箱。

流程：作者按 SDK 打包并提交源码、依赖与测试说明 → 自动校验和扫描 → 维护者审查关键权限、依赖及功能 → 对该版本最终负载清单签名 → 发布认证包。

自动检查优先复用现有包校验和 GameHub V3 签名实现，覆盖包路径与大小、协议兼容、未声明文件/依赖、基本生命周期、模拟测试和杀毒扫描。人工聚焦新增代码、网络、进程启动、提权及设备写入，不能把杀毒无告警当作审核完成。更新逐版本认证，不能给作者发一个无限制签名资格后自动信任其所有未来版本。

客户端先验证认证签名，再验证全体文件集合、清单与配置、每个文件摘要、接口版本和撤销状态；安装和启动时均检查受管负载。身份来自主体内置的项目认证公钥，不信任包自行带来的任意证书。包内的 reviewed=true、扫描结果截图或单独 SHA-256 都不能产生认证。

普通模式拒绝未认证、内容变更或已知撤销的包。作者使用隔离数据目录的显式开发模式调试未认证包，开发模式不承诺安全隔离，也不能使包进入普通分发。

初期只需要一个本地签名工具、客户端验签和静态发布/撤销清单，不建设账号系统、评分、自动审核后台或在线发证服务。撤销清单也由项目签名，可随主体更新或从静态地址拉取；离线只具备最后同步的撤销信息，不能承诺即时发现撤销。密钥轮换通过受信任主体更新处理。

认证只覆盖固定包内代码和依赖，不允许插件更新后自行下载替换可执行代码。外部驱动等例外单独审核、明确来源和用户操作，不能用通用下载执行入口绕过认证。内容发生变化必须重新打包认证。

## 2 复用现有签名代码

GameHub V3 的 DeveloperPackageSigner 已用 CMS/PKCS#7 对按路径排序的文件长度与 SHA-256 清单签名；DeveloperPackageValidator 和 PluginPackageValidator 有清单一致性检查。可提取成适合 Hhub 新清单的签名工具，不保留旧运行协议适配层。

CheckSignature(verifySignatureOnly: true) 只验证密码学签名，不会自动证明签名者被项目认可。因此新验签器必须独立固定项目认证公钥/证书，验证完整文件集合和撤销信息。作者元数据与认证签名者是不同概念。

认证体系无需购买公共 CA 代码签名证书即可在应用内建立项目私有信任，但不等于获得 Windows SmartScreen 声誉或系统驱动签名资格。签名格式细节在新包合同中固定后测试，不宣称现有 Hhub 已能加载认证包。

## 3 两类插件 共用一个体系

这是一套可选插件目录，不是主体的预装清单。用户只安装所需设备或功能。主体不捆绑完整设备库、EQ、监测、远控、系统设置或开发者工具；关闭功能不能代替不安装功能。后台保活仅由实际任务触发，未安装项不能产生业务代码加载或运行任务。

| 类别 | 用途 | 示例 |
| --- | --- | --- |
| 设备插件 | 精确识别设备并实现型号功能 | VT3X Max、EZ63、K03S |
| 功能插件 | 提供软件能力，可面向系统、音频端点或主体服务 | 通用 EQ、Windows 设置、手机遥控、系统监测 |

类别用于入口和目标选择，不产生两套包格式、协议或 SDK。后台任务不是第三种插件：任何插件都可以声明真实持续任务。插件是否有界面、是否提供公共服务、是否后台保活是独立属性。

共同合同包括：身份版本、认证、权限说明、可用目标、能力与状态、命令结果、页面、场景动作、启停、配置位置、退出恢复和依赖。具体设备或功能逻辑留在插件内，主体不包含品牌或 FxSound 专用分支。

普通设备插件可在独立普通用户进程中直接使用 Windows HID 等接口，不把实现一套全设备代理列为首版前提。经过认证的功能插件按其用途使用音频、系统或局域网接口。主体可校验自己的 API 权限，但不能据此宣称限制了原生代码的全部系统调用。

## 4 FxSound 类功能插件的开发方式

| 合同部分 | 通用 EQ 的定义 |
| --- | --- |
| 目标 | 用户选择的实际音频输出端点；不限定耳机品牌 |
| 能力 | 启停处理、EQ 频段、音效、预设、输出选择及真实运行状态 |
| 后台 | C# 管理生命周期及 WASAPI，必要时使用 C/C++ DSP 库 |
| 页面 | 原生或 WebUI，使用公共 UI 合同；认证涵盖 UI DLL、原生库与静态资源 |
| 保活 | 用户实际开启音频处理时维持后台；离开页面可以继续处理 |
| 停止恢复 | 释放音频资源并按明确规则恢复临时路由，尊重用户后续改选 |
| 数据 | 参数、预设及恢复记录存于该插件专属数据目录 |
| 场景 | 应用预设等已声明动作，与页面使用相同命令和确认结果 |
| 可选服务 | 向耳机插件提供版本化音频处理接口，复用处理能力 |

音频 PCM 留在音频处理进程，JSON Lines 只传控制、状态和必要的频谱概览。设备插件可以消费 EQ 服务，但不读取其私有文件或内部 UI 类型。服务缺失时设备信息仍可展示，音效功能明确不可用。

原生 UI DLL 仅在对应认证覆盖该 UI 负载且其使用公开 UI 合同后加载。认证准入减少未知代码来源，不给进程内 UI 增加故障或安全隔离。

## 5 首版开发者交付与开发顺序

开发包先提供同一套合同的两个完整模板：一个虚拟鼠标设备插件，一个具有开关、预设与持续任务的模拟功能插件。再提供可选音频服务消费示例。模板必须能独立构建与通过校验，不使用真实硬件默认值伪装验证结果。

文档采用一个离线入口，配套清单/消息 schema、SDK、模板与命令行校验器。分别讲清设备与功能插件，给出真实构建、调试、打包、提交认证步骤及 AI 开发入口，不要求作者阅读主体源码。

执行顺序：确定两类插件共同合同 → 最小 SDK 与两类模拟夹具 → 认证机制和 Hhub 主体改造 → 完成主体验收 → 重写 VT3X Max、通用 EQ 并逐步接入其他插件。主体验收前不迁移真实设备或功能插件；模拟夹具不随普通版安装。复杂隔离、多审核者、自动市场留待实际需要再做。验收明细见 Host-first-acceptance.md。

验签必须测试：可信包通过、陌生签名失败、任意负载/清单更改失败、添加/删除文件失败、已知撤销失败、更新重新认证及开发包不能混入普通模式。包认证与功能实机验收分开，二者都通过才发布具体硬件能力。
