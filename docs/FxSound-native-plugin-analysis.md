# FxSound 原生音频插件分析

日期：2026-11-02。分析基于本地 fxsound-app 提交 `4383180`、fxsound-driver 提交 `980335d` 和 Hhub 当前源码。仅静态检查，未编译、运行音频或安装驱动。

## 目标与结论

插件自己运行音频传输与 DSP，直接改变音频缓冲区。Hhub 负责插件生命周期、参数展示、场景派发。插件不调用或依赖 FxSound.exe。

源码支持这条路线：DfxDsp 与 AudioPassthru 已是两个 C++ 静态库，实际接口不依赖 JUCE 界面。仍需完成配置隔离、错误处理、线程同步、设备恢复和驱动部署，不能将现有库直接认定为可交付插件。

## 建议结构

```text
Hhub
  ↕ stdio-v1：命令、结果、状态
Hhub.Audio.Plugin.exe（C++ 原生后端）
  ├─ 协议入口与参数验证
  ├─ 配置、场景和预设持久化
  ├─ 音频生命周期与串行化参数更新
  ├─ DfxDsp 静态库
  └─ AudioPassthru 静态库（经改造）
       ↕
虚拟音频设备 → 插件处理 → 实际输出设备
```

优先使用原生可执行插件直接链接两个静态库。Hhub 插件协议不要求 C#，因此第一版无需额外增加 C# 宿主和 C ABI DLL。只有后续确实需要托管宿主时才增加 DLL 边界。

驱动是独立的系统依赖，不是插件进程内部加载的普通 DLL。源码中的 AudioPassthru 需要可识别且已启用的 DFX 虚拟设备；直接编译插件不会自动提供此设备。

## 已核对的接口

- `dsp/include/DfxDsp.h`：提供格式设置、音频处理、EQ、效果、预设和频谱接口。
- `audiopassthru/include/AudioPassthru.h`：提供初始化、DSP 挂载、设备枚举、目标选择、维护 tick 和恢复默认设备。
- `audiopassthru/src/AudioPassthru/AudioPassthruPrivate.cpp`：已有采集 → DSP → 播放循环；由 `processTimer()` 启动或重建工作线程。
- `dsp/DfxDsp.vcxproj`、`audiopassthru/audiopassthru.vcxproj`：为静态库工程，使用 MSVC v143；未发现它们的实现直接依赖 JUCE API。

## 必须改造的边界

1. **音频格式**：接口虽然使用 `short int*`，原有采集链实际把 float 缓冲区转型后传入，并明确说明采用 32 位浮点。不能按函数参数类型误当成 16 位 PCM；需给新后端明确格式契约并验证底层实现。
2. **配置隔离**：DSP 初始化使用 DFX 产品名，且存在注册表读取与写入路径。需要查清全部配置入口、迁移到插件命名空间或插件自有状态，避免与现有 FxSound 混用配置。
3. **初始化失败**：`DfxDspPrivate` 构造函数初始化失败时会显示 `TTEST/TEST` 消息框，并继续执行。无界面插件必须改成可传播、可清理的初始化错误。
4. **处理失败**：AudioPassthru 原循环忽略部分格式设置失败，并未检查 `processAudio()` 返回值。插件应有明确的错误、旁路或停止策略，不能失败后仍报告正在处理。
5. **线程安全**：音频线程处理缓冲区，控制线程接收参数。需审查各 setter 的共享状态，并将变更在受控边界应用；不能假定现有对象可跨线程任意调用。
6. **单声道**：源码保留单声道崩溃规避与跳过处理逻辑。首版应明确支持范围，对不支持的输出格式给出错误；蓝牙耳机切换模式需要实测。
7. **设备身份**：现有虚拟设备识别包含友好名称子串匹配。自有驱动命名或存在多个虚拟设备时需要改造，物理输出选择应保留端点 ID。
8. **实例限制**：AudioPassthru 的设备句柄与回调采用静态成员。首版按单音频引擎实例设计，不宣称可以同时独立处理多套输出。
9. **退出时限**：原音频线程停止等待上限为 3000 ms，Hhub 当前在 2500 ms 后强制结束插件树。需要协调停止契约，否则默认设备恢复可能来不及完成。
10. **崩溃恢复**：原析构函数负责恢复默认输出，但崩溃或强杀不会可靠执行析构。需要持久化接管前端点，并设计引擎退出后的恢复途径；恢复前检查用户是否已经主动切换设备。
11. **后台生命周期**：用户启用系统音效后，关闭页面不应释放音频进程。插件运行需求必须覆盖持续音频会话，并在明确停用时完成还原。

## 首版能力

- 查询驱动、真实输出设备和引擎状态。
- 开始与停止音频会话，选择输出设备。
- EQ 段数、频率、增益、Q、总增益和五类音效。
- 自有预设保存与加载，Hhub 场景应用。
- 状态区分：依赖缺失、就绪、运行、无音频、设备不可用、错误。

参数已接受、DSP 参数已应用和实际有音频流是不同事实，应分别报告。支持命令结果，但不能将进程存活当成音频正在处理。

Hhub 当前的通用命令和指标可承载基础控制。完整 EQ 曲线编辑需要后续扩展通用声明页面；音频后端应先独立验证。

## 验收顺序

1. 单独构建 DSP，以生成的浮点正弦与静音缓冲区测试真实处理：旁路、指定频段增益、非有限数、越界和静音稳定性。
2. 构建无 JUCE 音频后端，在具备可用虚拟设备的测试环境验证输入、处理、输出与格式变化。
3. 验证热插拔、输出失效、启动失败、正常停止、超时与强杀恢复；确认没有重复播放或虚拟设备回路。
4. 接入 stdio-v1，再验证命令回执、状态时效、场景切换和后台持续运行。
5. 最后完成交互与发布包验收。延迟、CPU 占用和音质效果以实测报告为准。
