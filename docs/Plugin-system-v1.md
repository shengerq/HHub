# Hhub 统一插件体系设计

日期：2026-11-09。状态：架构草案，尚未实现或发布为稳定 SDK。用户已选定 Hhub 主体，并明确要求先确定统一插件体系，再重写插件，不通过通用适配层强兼容历史插件。

最新范围按用户的个人维护约束收敛为 [认证准入与统一插件分类](Plugin-certification-and-kinds.md)：只有项目认证包可在普通模式运行，设备和软件功能插件使用同一套合同。首版不建设通用沙箱或强制硬件代理；此前隔离方案保留为历史参考。

## 1 产品与迁移边界

用户进一步明确：轻量首先体现为不包含用户用不到的功能。主体只交付基本窗口与导航、基础设备发现、插件安装/认证/启停/通信及必要公共接口。设备型号支持、EQ、系统监测、手机远控、Windows 设置和开发者工具均按需安装，不作为完整主体的必装负载；场景自动化等扩展也应按实际需要拆分，公共接口不等于内置整套功能。

不以“预装全部但默认关闭”替代按需安装。未安装功能不占其业务文件体积、不加载程序集、不创建 WebView 或后台任务；已安装但无需求的插件不常驻。共享运行时和公共 SDK 可复用，但不得以共享依赖为由附带全部功能实现。认证目录是分发入口，不是要求用户安装整套目录。

新增主体能力必须证明是多个插件所需的通用基础设施；只服务某项具体功能的代码留在插件中。主体支持稳定扩展点，不追求包含全部功能。以上是目标边界，现有 0.5 随附系统监测等行为仍需后续整改。

产品帮助玩家通过一个轻量应用调节不同品牌外设，减少多个厂商软件的安装与运行负担。主体负责公共能力；插件负责设备协议和可选功能；普通玩家无需安装开发者工具。首个完整设备目标为 VT3X Max，有线、无线都覆盖官方非固件升级功能。鼠标及接收器固件升级暂不实现。

GameHub 历史 C++ 插件、GameHub V3 SDK 插件与现有 Hhub 0.5 插件都是迁移来源，不是新体系必须直接加载的包。迁移复用经过核对的协议事实、算法、功能设计、测试及硬件证据；代码复用保留相应许可。按新合同重写清单、通信、界面接入和生命周期，必要时重写业务边界。

新合同版本标识必须与现有 schemaVersion=1、stdio-v1、UI API 1 区分。具体字段和线上标识在合同阶段确定。本文的操作与服务名称表示设计语义，不是已发布 API。

## 2 主体与插件的职责

主体提供设备目录、候选匹配、状态缓存、插件安装与监管、资源所有权、事务调度、场景、授权及界面公共服务。插件负责精确型号识别、厂商协议、真实状态读写、设备侧验证与恢复。

页面、场景与手机远控都经过同一个控制服务，不能分别直连硬件。主体不包含品牌专用分支；新增型号只增加插件及支持数据。设备插件、音频、系统设置、监测和远控共用一套合同，差异由能力声明表达。

第一版不强制新增常驻 Agent 服务。保留 Hhub 桌面主体，协调逻辑放入可测试的库；插件后台独立运行。未来内部进程拆分不能迫使开发者更换插件协议。

## 3 包与运行环境

统一包为 ZIP 容器，清单描述稳定 ID、发布者、版本、协议主版本、平台和架构、入口、所需主体能力、权限、设备匹配、能力、页面与许可证。安装目录与用户数据分离，不允许插件把自身安装目录用作配置目录。

设备包可以支持经过验证的多个型号，但逐型号、固件及传输声明支持范围；不强制一个品牌一个包，也不把一种连接拆成一种插件。候选匹配成功后仍需插件确认实际目标。

后台业务为普通用户权限的独立进程。官方推荐 C#，使用主体提供的版本化 .NET 运行环境；原生 C++ 等实现可用 EXE。第三方实现遵守进程协议即可，不绑定 C#，不依赖跨语言 ABI。

主体管理启停与异常；插件不另外创建托盘或要求玩家打开另一个控制软件。专用运行环境必须声明来源、用途、体积与清理规则，不把 Node.js 等依赖强加给所有插件。

## 4 进程协议与状态

第一版选择 UTF-8 JSON Lines 作为跨语言进程传输，但使用新体系独立标识，不伪装成旧 stdio-v1。stdout 只输出协议，stderr 输出诊断。消息大小、超时、并发及队列上限在协议规范与一致性测试中固定。

协议覆盖握手与版本协商、设备发现与变化、完整读取、状态订阅、事务执行、取消和关闭。握手完成前不执行控制，不支持的主版本在调用业务前拒绝。

请求 ID、事务 ID 和设备 revision 分开定义，分别用于消息关联、一次操作及并发基线。发送完成不代表硬件生效；超时、断连后不自动重放可能已执行的写操作。幂等、去重范围与结果查询进入合同测试，不可幂等操作不能重复执行。

完整与增量状态使用不同的明确消息类型。状态包含设备身份、revision、来源时间及确认状态；主体另外记录接收时间。电量等子项保留自身采样时间，不把重发缓存当新采样。

断连、不支持、未实现、依赖缺失、过期、执行失败及最终状态未知分别表达。稳定错误码与显示文案分离，不依赖中文或英文字符串判断结果。

## 5 设备身份与能力模型

主体提供不透明设备 ID、关联接口及传输信息。VID/PID 只是候选条件，不能独自证明型号或同一物理设备。有线、无线、接收器空载、双连接及同型号多设备分别验证，身份不明确时不能猜测写入目标。

能力具有稳定 ID、JSON schema、读写属性、值域、默认值、持久化行为、资源范围、风险和支持条件。统一支持标量、对象与数组，覆盖 DPI 档位表、按键映射、宏、逐键磁轴参数、EQ 与灯效。

同一能力 ID 的含义、单位、值类型不能因设备不同静默改变；设备可声明不同支持范围。厂商专用能力使用命名空间。先确定公共语义与扩展机制，不一次性枚举未来所有设备功能。

控件由真实能力驱动。声明存在、模拟器通过、硬件验证和正式发布分别记录；不得把内存初始值当硬件读数或生成虚假的默认配置。

## 6 事务与资源所有权

主体负责单写者资源协调、revision 检查、参数校验和事务调度；插件负责实际报文、真实读取、执行、独立读回与设备侧恢复。SDK 提供统一流程，插件实现硬件边界。

标准流程为读取基线、核对身份和参数、执行、独立读回、发布确认状态。失败时恢复并验证恢复。结果至少区分：确认应用、拒绝且未执行、验证恢复、最终状态未知。未知状态阻止后续自动写入，重新读取确认后恢复。

回滚边界由实际设备决定，不承诺所有操作或跨设备场景具备真正原子性。恢复出厂与恢复插件备份分别定义。高风险动作需要主体确认和明确恢复方案；本阶段不提供固件升级。

## 7 界面与插件协作

原生 WinUI 与 WebUI 为同一体系下两种页面方式。插件组织专业内容，主体提供窗口导航、设备上下文、主题、状态订阅和控制服务。无需页面的插件不强制携带浏览器。

新 WebUI 由清单直接声明本地入口，通过统一桥接访问公共服务，不要求每个插件额外编写原生 UI 包装 DLL。页面不可见时销毁界面、订阅和计时器，必要后台任务单独维持。

原生 UI 使用独立、最小化、版本化的合同程序集，不引用 Hhub.App，也不把 Hhub.Core 的所有公开类型当 SDK。主体存储类型、窗口对象和内部设备模型不得成为外部永久依赖。现有 PluginUiContext 不能未经整理就冻结为稳定 API。

原生 UI 必须被项目认证覆盖并使用公开 UI 合同后才可加载，第三方作者可提交认证，不按作者身份另建一套接口。原生 UI 在主体内没有安全或故障隔离。WebUI 与声明式页面同样可选；原生兼容矩阵验证确切 Windows App SDK、运行时和旧 UI DLL，不能只比较版本整数。

插件协作通过有版本的公共服务。例如耳机消费音频处理服务，远控调用主体控制服务。提供方缺失时降级，不读取其他插件私有配置、不调用内部类型或 UI 树。多个提供方由主体选择并管理资源，不硬编码一个插件 ID 为永久唯一提供方。

## 8 生命周期与轻量目标

主体本身的安装、卸载、更新、数据迁移及回退也是主体验收范围。更新须保留并正确解释旧插件预设、场景和设置；不兼容或迁移失败时不能静默丢弃。卸载必须停止并移除受管插件、后台、缓存及启动注册，个人数据单独明确选择。细则与场景见 [主体验收](Host-first-acceptance.md)。

默认按需运行。页面、读取、执行中操作及真实持续任务形成需求；安装成功、导航可见或接收器存在本身不构成常驻理由。用户停用优先。

持续 EQ、必要电量监听等声明用途、活动状态和停止行为，不用空心跳无限保活。优先设备事件与有界轮询，未变化状态减少重复消息及刷新。

停止、更新、卸载与异常退出分别规定持久配置及临时系统修改的处理。板载设置通常保留；临时音频路由恢复须尊重用户后续修改。更新暂停新命令、停止进程、校验新包、备份和原子切换；数据迁移失败能够恢复。

性能统计主体、插件和 WebView2 的总 CPU、内存、启动耗时，分别测量冷启动、前台调节、后台空闲与持续任务。参考设备测量后确定预算，不以清空工作集或只统计主体证明轻量。

## 9 权限与安装信任

首版依靠集中审核和项目签名控制包准入，不开放未知包在普通模式执行。权限说明用于审核、告知与主体 API 校验，独立普通用户进程不能限制原生代码的全部系统调用。设备插件可直接使用 Windows HID，功能插件按认证范围使用相应接口，不宣称操作系统沙箱。

统一安装校验路径、资源上限、清单、内容摘要和兼容性，校验完整负载清单的项目认证签名与已知撤销状态。认证按版本，不接受任意作者自签为可信；认证包内容不能静默下载替换。提取复用 GameHub V3 的 CMS 签名代码，不保留旧运行协议兼容层。扫描与审核辅助准入，认证不等于绝对安全。具体格式冻结并实现前不宣称认证已可用。

主体不默认提权。外部驱动或权限提升逐项声明并由用户主动处理；系统监测的历史特殊授权不能推广到所有插件。

## 10 稳定发布与未来兼容

兼容承诺从新体系首个稳定 SDK 起算。旧插件按统一合同一次性重写，不长期维护通吃历史协议的适配层。

清单、进程协议、UI 合同和公共服务分别版本化，插件版本与主体版本分开。主版本内不删除字段、不改变类型、默认值、单位、动作含义或成功语义。新增可选字段保持旧行为，新能力经声明和协商启用。

不兼容语义进入新主版本，提供迁移说明及明确旧版本支持期限，不能每次主体更新都要求作者重写。平台最低版本、支持期限和弃用周期在首个稳定 SDK 前固定。

公开 SDK 包含机器可校验的清单与协议 schema、独立合同包、C# 与原生示例、错误码、生命周期说明、打包检查器和一致性测试。作者只阅读 SDK 即可开发，无需阅读主体源码。

主体每次发布使用历史稳定示例与已发布插件原包回归，不重新编译旧插件来掩盖兼容问题。覆盖握手、读取、事务、关闭、页面加载，以及新插件在旧主体缺少能力时明确拒绝。安全修复需要收紧行为时公布影响及迁移路径。

## 11 执行顺序

用户已明确先后顺序：确定插件体系 → 改造并验收 Hhub 主体 → 按已确定接口重写和逐步加入真实插件。在主体验收前，不以 VT3X Max、FxSound 或其他真实插件的迁移作为主任务。模拟插件仅用于验收主体，不随普通版预装。具体验收清单见 [主体优先实施与验收](Host-first-acceptance.md)。

| 阶段 | 交付 | 退出条件 |
| --- | --- | --- |
| 体系与合同确定 | 清单、通信、能力、事务、页面、生命周期和认证规范 | 同时表达设备及功能插件；明确稳定边界、版本和成功语义 |
| 最小 SDK 与测试夹具 | 独立合同、校验器、模拟设备和模拟功能插件 | 不依赖主体内部库；可表达复杂值、预设和持续任务 |
| 主体改造 | 精简主体、认证安装、启停通信、页面及公共服务 | 不内置具体业务；所有公共调用经过统一接口 |
| 主体验收 | 自动化结果、可运行主体验收版、SDK v1 候选 | 空主体、认证、异常、更新恢复及两类模拟插件全部通过 |
| 真实插件接入 | 先 VT3X Max，再通用 EQ 与其他插件 | 使用已确定接口，逐个验收，不为插件增加主体品牌分支 |
| 对外稳定发布 | 完整 SDK、文档、兼容矩阵、认证包 | 主体验收与对应真实插件证据齐备；后续使用已发布原包回归 |

VT3X Max 保留为主体验收后的首个完整设备目标。键盘、EQ 等类型通过合同和模拟夹具提前覆盖，不提前迁移真实插件。GameHub 的分析、协议和测试用于校对需求，不迁入整套旧包运行系统。

## 12 本轮实现核对与证据

现有 Hhub 使用 schemaVersion=1、stdio-v1、最低主体 0.5.0、UI API 1 和能力检查。已有 DLL 共享 .NET 启动器及 EXE 后台。现有通用参数表单仅有 number/string/boolean，不等于新复杂能力 schema。

现有原生 UI 引用 Hhub.Core；WebUI 仍需原生模块包装；协作按插件 ID 与命令绑定。以上是待整理边界，不是新体系已达标。

2026-11-09 用工作区 .NET 10.0.403 编译并执行现有 Core 检查。全量运行在协议检查后因临时目录 Hhub.Core.Tests.exe 访问被拒绝而终止，退出码非零，不计为通过。日志为工作区根目录 hhub-core-baseline.log。

单独用 --validate-packages 在临时目录安装、校验并卸载 8 包，退出码 0：audio 0.10.0、headset-k03s 0.1.1、hp-overture 0.1.4、keyboard 0.1.0、mouse 0.3.3、phone-remote 0.1.2、system-monitor 0.5.7、windows-settings 0.4.2。只证明现有包清单、路径及安装检查通过，未运行插件、UI 或硬件。日志为工作区根目录 hhub-package-compatibility.log。

本轮未改运行接口、未重写设备代码、未运行硬件命令，也未将本设计宣布为已发布 SDK。
